# 汎用アプリケーション設計ガイドライン

あらゆる規模・ドメインのソフトウェアプロジェクトに適応しやすい構造とプラクティスをまとめたリファレンスです。  
個別プロジェクトでは、本ガイドラインを基盤に具体的な要件へ適合させてください。

---

## 1. 目的と適用範囲

- 技術スタックに依存しないアーキテクチャ指針を提供する。
- 小規模 MVP からエンタープライズシステムまで段階的に拡張できる構造を示す。
- クリーンアーキテクチャ（Hexagonal / Ports & Adapters / Onion）の原則を基盤とし、モノリスでもマイクロサービスでも適用可能な境界設計とライフサイクル管理を示す。
- 機能要件と非機能要件（性能・安全性・信頼性等）のバランスを評価する際の共通言語となる。

### 1.1 非対象（Non‑Goals）

- 具体的製品・クラウド・フレームワーク固有の手順は本書の規範ではない（参考情報に留める）。
- 実装細部（ディレクトリ構成、API の仕様詳細等）はプロジェクト文脈で決定し、本書は意思決定の原則と評価軸のみを提供する。

### 1.2 規範用語（Normative Language）

- 本書における「MUST/必須」は常に満たすべき要件、「SHOULD/推奨」は状況により代替可だが理由の明記が必要、「MAY/任意」は選択可を示す（RFC 2119 準拠の解釈）。
- 規範的記述と参考的記述を区別し、前者はレビュー/監査の対象とする。

## 2. 基本原則

### 2.1 ビジネス整合性

- **価値優先**: アーキテクチャはビジネス目標・ユーザー価値を最大化する手段として設計する。
- **適応性**: 環境・要件の変化に応じて段階的に調整できるよう、可変部分と固定部分を明確化する。

### 2.2 技術原則

- **Single Responsibility**: モジュールは単一の関心事に集中し、変更理由を最小化する。
- **Separation of Concerns**: レイヤ、境界、コンポーネント間の責務を明確化し循環依存を回避する。
- **YAGNI/KISS**: 将来要件を見越した過剰設計を避け、シンプルな解に余地を残す。
- **DRY**: 再利用可能な知識・ロジックは共通化するが、無理な抽象化は避ける。
- **Observability by Design**: 監視性・トレーサビリティを最初から考慮する。

### 2.3 コラボレーション原則

- **ドキュメントファースト**: 設計意図と意思決定を言語化し、チーム全体で共有する。
- **自動化優先**: テスト・デプロイ・品質チェックを可能な限り自動化する。
- **セキュリティシフトレフト**: 早期段階で脆弱性リスクを洗い出し、継続的に検証する。

## 3. リファレンスアーキテクチャ

### 3.1 レイヤリングモデル

| レイヤ                          | 主な責務                                                                 | 注意点                                       |
| ------------------------------- | ------------------------------------------------------------------------ | -------------------------------------------- |
| **Presentation / Interface**    | UI、API、CLI、イベント入口。ユーザー／外部システムとの接点。             | ステートレス原則、入力検証、CSRF/XSS 対策。  |
| **Application / Orchestration** | ユースケース、ワークフロー、トランザクション制御。ドメイン操作の調停。   | ドメインロジックの重複を避ける。             |
| **Domain / Core**               | ビジネスルール、エンティティ、ドメインイベント、サービス。               | 外部依存を最小化し、テスト容易性を確保。     |
| **Infrastructure**              | データベース、外部 API、メッセージング、ファイルシステム等へのアクセス。 | Adapter パターンで抽象化し、差し替え可能に。 |
| **Cross-Cutting**               | セキュリティ、ロギング、キャッシュ、構成管理、国際化等。                 | ポリシーやミドルウェアで横断的に適用。       |

### 3.2 モジュール境界

- **機能単位の分割**: Feature Sliced、Bounded Context、サービス境界等を採用し、ビジネス能力ごとに独立性を高める。
- **依存方向のルール**: 上位レイヤ→下位レイヤの単方向依存を基本とし、インターフェース（Port）で反転可能にする。
- **契約駆動**: REST/gRPC/OpenAPI/GraphQL/イベントスキーマ等で通信契約を明文化し、消費者駆動契約テストを活用する。

- **変更隔離（Change Isolation）**: 変更の多い領域をインターフェース越しに分離し、DIP（依存性逆転）、Seams、Anti‑Corruption Layer 等で影響範囲を制御する。
- **契約の進化**: 前方/後方互換を意識し、段階的廃止（Deprecation）、互換期間、フォールバック戦略を定義する。

### 3.3 クリーンアーキテクチャ系の原則

- **同心円構造**: エンティティ（ドメインモデル）→ユースケース（アプリケーションサービス）→インターフェース（アダプタ）の順に内側から外側へ依存する。内側は外側の詳細に依存しない。
- **ポート＆アダプタ**: インターフェースを「ポート」として定義し、UI、DB、外部 API 等の具体実装は「アダプタ」で差し替える。これによりレイヤードモノリスでもマイクロサービスでもドメインを保護できる。
- **テスト容易性**: ユースケース層までを純粋なコードとして保つことで、モックを用いた高速なユニット／統合テストが可能になる。外部依存をアダプタに閉じ込めることで CI/CD パイプラインの安定度を高める。
- **段階的分割**: 初期は単一デプロイ（モノリス）で開始しつつも、コンポーネント境界を明確化しておくことで、必要になったタイミングでサービス分割・サーバーレス化などの移行コストを抑えられる。
- **技術選択の柔軟性**: アダプタを介して技術依存を局所化することで、データストア／通信プロトコル／UI 技術を段階的に置き換えられる。非機能要件の変化にも追随しやすい。

### 3.4 併用する代表的アーキテクチャスタイル

| スタイル                           | 主な用途                                                     | クリーンアーキテクチャと組み合わせる際のポイント                                                                                   | 留意点                                                                           |
| ---------------------------------- | ------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------- |
| **レイヤード／モジュラーモノリス** | 小規模～中規模の単一デプロイ。既存資産のモダナイズ。         | ドメイン／ユースケース層を分離し、データアクセスや UI をアダプタ化。モジュール境界を Bounded Context として維持。                  | レイヤが肥大化しやすいので、モジュール境界の循環依存を禁止する。                 |
| **マイクロサービス**               | 俊敏なチーム分割、独立スケール、複雑ドメイン。               | 各サービス内部をクリーンアーキテクチャで統一し、サービス間契約（API, イベント）をポートとみなす。共有ライブラリは最小限に。        | 分散トレーシング、サービスメッシュ、契約テストなど運用・品質確保のコストが高い。 |
| **イベント駆動 / CQRS**            | 高トラフィックの非同期処理、リアルタイム分析、多様な購読者。 | コマンド／クエリをユースケース層で分離し、イベントブローカーをアダプタとして接続。イベントスキーマをポート契約として管理。         | イベント整合性や再送制御が複雑。可観測性とデータガバナンスを強化する。           |
| **サーバレス / FaaS**              | バースト負荷、短期イベント、運用コスト最適化。               | ドメインコアを共通ライブラリとして保持し、各ファンクションをアダプタ実装にする。ステート管理はドメインルールに準じた外部ストアで。 | コールドスタート、タイムアウト制約、プラットフォーム依存を考慮。                 |
| **イベントソーシング / DDD**       | 履歴管理、監査、複雑な集計要求。                             | ドメインイベントをエンティティの主要出力とし、イベントストアをアダプタ化。クエリ用リードモデルは独立したアダプタとして構築。       | イベントの再生・整合性維持が難しい。ガバナンスと再構築手順を文書化する。         |

| **エッジ / オフラインファースト**  | ネットワーク不安定環境、低遅延要件。                         | 同期/衝突解決をユースケースに組み込み、データ一貫性モデルを明示。                                          | 一時的な不整合と再送戦略、セキュアなローカル保存を考慮。                         |
| **マルチテナント（SaaS）**         | 複数顧客の論理隔離と運用効率。                               | テナント分離（データ/構成/実行）、拡張ポイント設計、課金・配布の契約管理。                                  | ノイズネイバー、データ越境、リージョン要件、規模差の吸収。                       |
| **データ/ML パイプライン**         | バッチ/ストリーム処理、モデル運用。                           | データ契約、スキーマ進化、再現性（Lineage/バージョン）を設計に組み込む。                                      | ドリフト検知、品質管理、ガバナンス/説明責任の確保。                               |
| **ワークフロー/BPM 指向**          | 人/システム間の手続や承認を可視化。                           | ドメインルールとプロセス定義を分離し、ワークフローはアダプタとして接続。                                      | 長期実行トランザクションの可観測性と回復手順。                                     |

## 4. クロスカッティング設計

### 4.1 セキュリティ

- **ゼロトラスト**: すべての入口で認証認可、最小権限、入力検証を徹底。
- **データ保護**: 暗号化（保存時・通信時）、PII/PHI/GDPR/PCI等の法規制を遵守。
- **監査性**: 重要操作を監査ログとして記録し、改ざん検知と追跡を可能にする。

- **供給網セキュリティ**: SBOM 生成、依存バージョンのピン留め/検証、署名/署名検証、継続的な脆弱性監査を行う（MUST）。
- **インシデント運用**: 体制/手順/通報基準/ポストモーテム（責任追及ではなく学習）を明文化（SHOULD）。

### 4.2 パフォーマンスとスケーラビリティ

- **容量計画**: 期待トラフィックと SLA を明文化し、ロードテストを実施。
- **キャッシュ戦略**: アプリケーション／データ／CDN キャッシュを使い分け、整合性モデルを定義。
- **スケール戦略**: 垂直／水平スケール、シャーディング、キューイングを組み合わせ、バックプレッシャーを設計。

- **パフォーマンス予算**: 応答時間/スループット/リソース使用の予算を設定し、逸脱時の是正手順を定義（MUST）。
- **継続的計測**: 本番に近い環境で継続測定し、回帰検知を自動化（SHOULD）。

### 4.3 オブザーバビリティ

- **ログ**: 重要なビジネスイベントとエラーを構造化ログで出力する。
- **メトリクス**: サービスレベル（SLO/SLA/SLE）、リソース利用率、カスタム KPI を収集。
- **トレーシング**: 分散トレース（OpenTelemetry 等）でレイテンシーを可視化。
- **アラート**: 明確な運用基準とエスカレーション手順を定義。

- **SLI/SLO/SLA とエラーバジェット**: 主要なユーザ体験を表す SLI と目標 SLO を定義し、エラーバジェット消費に基づくリリース/機能フリーズ方針を運用（MUST）。
- **ランブック**: 代表インシデントの手順、ダッシュボード、エスカレーションを整備（SHOULD）。

### 4.4 データ管理

- **データモデル**: 正規化・非正規化戦略、イベントソーシング、CQRS 等を要件に応じて選択。
- **整合性**: ACID／BASE モデル、最終整合性、データ品質ルールを明確化。
- **マスタデータ／参照データ**: ガバナンスと同期戦略を定義。
- **バックアップ／復旧**: RPO/RTO に基づくバックアップ、DR、フェイルオーバー手順を整備。

### 4.5 コンフィグレーションとリリース管理

- **12-Factor 原則**: 環境変数による設定管理、ステートレス設計を推奨。
- **フィーチャーフラグ**: 新機能の段階的リリースや実験を安全に行う。
- **リリース戦略**: Blue/Green、Canary、A/B テスト、ロールバック手順を整備。

### 4.6 信頼性とレジリエンス

- **タイムアウト/リトライ**: 指数バックオフ/ジッタを用い、冪等性を確保（MUST）。
- **サーキットブレーカ/バルクヘッド**: 障害の波及を防ぎ、重要機能を優先（SHOULD）。
- **デグレード運転**: 代替経路/機能制限で最低限の価値を維持（SHOULD）。
- **重複排除と順序保証**: 受信側での冪等キー/シーケンス管理（MAY）。

### 4.7 データガバナンスとプライバシー

- **データ分類/属性**: 機微度/保有期間/所在地/アクセス制御を明確化（MUST）。
- **最小化/目的外利用防止**: 収集と保有を最小限にし、二次利用はポリシー準拠（MUST）。
- **削除/移植/監査**: DSR 対応、監査証跡、データ整合手順を用意（SHOULD）。

### 4.8 コストとサステナビリティ

- **コスト/KPI**: Cost per 取引/ユーザ等の単価指標を定義（SHOULD）。
- **FinOps/GreenOps 原則**: スケールダウン、自動停止、効率メトリクスで継続改善（SHOULD）。
- **パフォーマンス予算との整合**: コスト/性能のトレードオフを透明化（MAY）。

## 5. 開発ライフサイクル

### 5.1 環境定義

- **最低限の環境**: ローカル、統合（Staging）、本番（Production）。
- **拡張環境**: QA、UAT、Performance、Security、Sandbox 等。プロジェクト規模に応じて追加。
- **一貫性**: IaC（Infrastructure as Code）で環境差異を最小化。

### 5.2 CI/CD パイプライン

- **ビルド**: リンター、静的解析、依存関係チェック、コンパイル／バンドル。
- **テスト**: 単体→統合→E2E→セキュリティ→パフォーマンスの順で自動化。
- **デプロイ**: Infrastructure provisioning、アーティファクト配布、環境毎の設定注入。
- **ゲート**: 品質メトリクス（コードカバレッジ、セキュリティスキャン、パフォーマンス閾値）を可視化し、合格基準を設定。

- **ソフトウェア供給網**: SBOM 生成、依存の署名/検証、既知脆弱性スキャン、ライセンス遵守チェックをパイプラインに組み込む（MUST）。

### 5.3 バージョニングと変更管理

- **Semantic Versioning**: API／サービスの互換性を明確にし、破壊的変更は計画的に実施。
- **Change Advisory Board（必要時）**: 大規模組織では重大変更をレビューするプロセスを設ける。
- **リリースノート**: 新機能・修正・既知の問題・影響範囲を記録。

- **段階的廃止戦略**: 非推奨化の告知→移行ガイド→サンセットの順で管理（SHOULD）。
- **互換期間/フォールバック**: 後方互換の提供や互換レイヤで移行を支援（SHOULD）。

## 6. 品質保証とテスト戦略

| レベル                         | 目的                                               | 推奨ツール／手法                             |
| ------------------------------ | -------------------------------------------------- | -------------------------------------------- |
| **静的解析**                   | 早期にバグ・スタイル違反・セキュリティリスクを検出 | Linter, Type Checker, SAST                   |
| **単体テスト**                 | 関数・クラスの振る舞い保証                         | テストフレームワーク（xUnit）, モック/スタブ |
| **コンポーネント／統合テスト** | モジュール間連携を検証                             | Test doubles、契約テスト、API テスト         |
| **E2E／UI テスト**             | ユーザーフロー全体を検証                           | ブラウザ自動化、BDD                          |
| **性能テスト**                 | SLA／SLO 達成を確認                                | ロードテスト、ストレステスト、容量テスト     |
| **セキュリティテスト**         | 脆弱性・権限漏れを検出                             | DAST、IAST、ペネトレーションテスト           |
| **回帰テスト**                 | 変更による影響を検知                               | テスト自動化スイート、スモークテスト         |

- **テストデータ管理**: 個人情報保護に留意し、マスキングや合成データ生成を活用。
- **品質メトリクス**: テストカバレッジ、欠陥密度、MTTR、デプロイ頻度等を継続的にモニタする。

- **契約テスト**: API/イベント契約の消費者駆動テストで進化的変更を安全化（SHOULD）。
- **プロパティテスト**: 入力空間が広いドメインに対して性質ベースで検証（MAY）。
- **データテスト**: スキーマ/品質/鮮度の検証をパイプライン化（SHOULD）。
- **自動化判断基準**: リスク×頻度×影響で自動化優先順位を定義（MUST）。

## 7. チームとプロセス

- **ロール定義**: プロダクトオーナー、テックリード、アーキテクト、開発者、QA、SecOps、SRE 等の責務を明確化。
- **ガバナンス**: アーキテクチャレビュー、ADR（Architecture Decision Record）、設計ガイドミーティングで意思決定を共有。
- **知識共有**: ドキュメント、アーキテクチャダイアグラム、技術ブログ、内製勉強会を推奨。
- **継続的改善**: レトロスペクティブ、バリューストリーム分析、技術負債の可視化を習慣化。

- **アーキテクチャ逸脱（例外）プロセス**: 逸脱の申請/評価/時限付き承認/是正計画/サンセットを定義（MUST）。
- **ADR ライフサイクル**: 提案→レビュー→承認→施行→廃止までの状態と責任者を明確化（SHOULD）。

## 9. アーキテクチャ評価チェックリスト

- ビジネス目標と品質特性は明確か？
- レイヤ構造とモジュール境界に循環依存はないか？
- セキュリティ・性能・可用性の非機能要件を満たす対策が計画されているか？
- テスト戦略と自動化は十分か？
- オブザーバビリティと運用手順は整備されているか？
- 変更管理とリリース戦略は定義されているか？
- 文書化と知識共有の仕組みは存在するか？

- レジリエンス（タイムアウト/リトライ/遮断/デグレード）は設計されているか？
- データガバナンス/プライバシー要件は満たされているか？
- 契約（API/イベント）の進化戦略と互換期間は定義済みか？
- SLI/SLO/SLA とエラーバジェット運用は定義/監視されているか？

## 付録 A: 用語集（抄）

- SLI/SLO/SLA: サービスの指標/目標/合意水準。
- エラーバジェット: 許容不可用時間。消費状況に応じた意思決定指標。
- ADR: Architecture Decision Record。設計上の重要な意思決定の記録。
- SBOM: Software Bill of Materials。ソフトウェア構成要素一覧。
- DIP/Seams/ACL: 変更隔離のための設計パターン。

## 付録 B: ATAM シナリオテンプレート（簡易）

- 刺激（Stimulus）: 何が起こるか
- 環境（Environment）: どの状況で
- 源（Source）: どこから
- アーティファクト（Artifact）: 何に影響するか
- 応答（Response）: どう振る舞うべきか
- 尺度（Response Measure）: どう測るか

## 付録 C: モデリング指針（C4 等）

- Context/Container/Component/Code の粒度で図示し、利害関係者に応じた詳細度を選択。
- 図は単一の真実としてリポジトリにバージョン管理し、変更時に更新する。
